# 06 · 内容生产流水线：百科词条的工业化生产与质检

> [itswe.com](https://www.itswe.com) 建站文档 · 内容篇。一个技术 wiki 如何在没有专职编辑团队的情况下，工业化地产出数百篇质量一致、数值可溯源的词条。重点在**质检纪律**——它比生成技术更决定内容质量。

## 核心理念

1. **源文件制**：内容以纯文本源文件管理（git 可版本化、可机检、可批量改造），wiki 数据库只是发布目标
2. **机检不过不发布**：每条内容规则都落成自动 lint，人工只处理机器判定不了的少数项
3. **发布是流水线不是操作**：stage → 校验 → dry-run → 发布 → 后置校验，缺一步即回滚

## 源文件结构

```
content/
├── main/<slug>.wiki           # 内容词条
├── category/<slug>.wiki       # 分类描述页
├── 00-meta/                    # 元页面（关于/隐私/首页区块）
└── VERIFIED_VALUES.md          # 标准号白名单（数值溯源的唯一依据）
```

源文件头部 front-matter：

```
// DISPLAYTITLE: 接触线磨耗
// CATEGORY: operation
// TIER: 基础
```

- `DISPLAYTITLE` 走 MediaWiki 魔术字，页面标题与 slug 解耦
- `CATEGORY` 决定分类归属，分类页由数据文件生成
- ⚠️ 生成式分类页（`--generate`）会**整体覆盖**手工增补——手工内容必须先并入生成数据源

## 质检：lint 规则集

每批内容发布前逐页过检，全绿是交付门槛（全量过检）：

| 规则 | 说明 |
|---|---|
| E7 标准号白名单 | 站外引用的标准编号必须先登记（防幻觉标准号/错误版本号） |
| 锚句逐字锁定 | 关键句与源一致，防止改写走样 |
| 加粗语法 | wiki 用 `'''` 不用 `**`（Markdown 混入检测） |
| 禁词清单 | "全文如下/摘自百度百科/搜狗百科"等搬运痕迹零容忍 |
| 骨架完整性 | 必备章节齐全、字数下限（防薄页） |
| 数值格式 | 区间用半角 `~`，公式用 `<math>` 标签 |
| 断链检查 | 站内链接目标存在（白名单豁免分类链接） |

## 发布流水线

```
本地 stage → 上传图片资源 → publish --dry（全量 lint）→ publish
    → 同步 llms/og/sitemap → 清缓存 → OPTIMIZE searchindex → 后置抽查
```

### 后置抽查（血泪教训）

**不能只验新页 200**。必须抽查"更新类"目标页的 wikitext 实际内容——曾因导入路径多一层目录，深层文件侥幸成功、浅层文件被导成垃圾页且**正确标题静默未更新**，只有抽查 wikitext 才能发现。

验证分类页要看**去标签后的可见文本**（HTML 里有链接 ≠ 用户能看到），并确认侧栏导览存在。

### 批量编辑后的数据库维护

每次批量导入后：`OPTIMIZE TABLE searchindex`（FTS 增量段膨胀是确定性事件，见 [02 · 性能篇](02-mediawiki-performance.md)）。

## 直改通道的使用边界

单页热修可走 MediaWiki API 直改（免全量导入），但有严格边界：

- ✅ 适用：手工构造的纯文本（重定向行、错字修正）
- ❌ 禁止：含 front-matter 的源文件内容——API 直写会把注释写进正文、魔术字丢失
- ⚠️ 中文标题会命中别名重定向页，**编辑正文一律用英文 slug**
- 线上直改后**必须回写源文件仓库**，否则下次全量导入即回滚

## 规模化经验

- 批量改写并发 ≤2，更高并发触发上游速率限制
- 每批留 notes/ 记录来源 URL 与存疑项，可回溯
- 薄页（<4KB）单独建清单限期增补，防止知识库被弱内容稀释
- 生成内容与人工内容用同一套 lint 标准时，质量才能"底线一致、上限靠人"
